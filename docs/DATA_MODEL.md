# OpsMemory — Data Model

## MongoDB Collection: `incidents`

Database: configured via `MONGO_DB` (default: `opsmemory`)
Collection: `incidents`

### Schema

| Field | Type | Notes |
|-------|------|-------|
| `incident_id` | string | Unique sequential ID, format `INC-0001`. Generated by `db.next_incident_id()`. |
| `title` | string | Short human-readable summary of the incident. |
| `service` | string | One of the 6 services (see below). |
| `severity` | string | `SEV1`, `SEV2`, or `SEV3`. |
| `error_log` | string | Raw log lines or stack trace captured at incident time. |
| `symptoms` | string | What the on-call engineer observed (alert text, user reports, dashboards). |
| `root_cause` | string | Confirmed root cause; empty string while `status = open`. |
| `fix_steps` | list[string] | Ordered resolution steps; empty list while `status = open`. |
| `resolution_minutes` | int | Time taken to resolve in minutes; 0 while `status = open`. |
| `status` | string | `open` or `resolved`. |
| `created_at` | datetime | UTC timestamp when the incident was opened. |
| `resolved_at` | datetime or null | UTC timestamp when resolved; null while open. |

### Example Document

```json
{
  "incident_id": "INC-0001",
  "title": "payments-api — HikariPool connection timeout causing 5xx flood",
  "service": "payments-api",
  "severity": "SEV1",
  "error_log": "2025-09-28T08:12:15.342Z ERROR HikariPool-1 — Connection is not available...",
  "symptoms": "5xx error rate climbed to 40%. HikariPool-1 timeout errors in logs.",
  "root_cause": "DB connection pool exhausted after traffic spike",
  "fix_steps": [
    "Increase connection pool size to 50",
    "Restart payments-api pods",
    "Add pool-timeout alert at 80% utilisation"
  ],
  "resolution_minutes": 22,
  "status": "resolved",
  "created_at": "2025-09-28T08:12:00Z",
  "resolved_at": "2025-09-28T08:34:00Z"
}
```

## Seed Data Rules (`data/generate_incidents.py`)

### Generation

- **Total incidents:** 40 (exactly)
- **Determinism:** `random.seed(42)` — running the script twice produces identical output
- **Method:** Template-based, no LLM required

### Root-Cause Families (8 × 5 = 40 incidents)

| # | Family | Root Cause | Fix Pattern |
|---|--------|-----------|-------------|
| 1 | `db_pool_exhaustion` | Connection pool exhausted | Raise pool size, restart pods, alert |
| 2 | `redis_oom` | Redis maxmemory exceeded | Raise maxmemory, set eviction policy, flush stale keys |
| 3 | `tls_cert_expired` | TLS certificate expired | Renew cert, reload ingress, add expiry monitor |
| 4 | `bad_deploy` | Misconfigured env var in deploy | Rollback, correct env var, redeploy |
| 5 | `kafka_consumer_lag` | Consumer group fell behind | Scale consumers, reset stuck offset |
| 6 | `disk_full` | Disk full from log growth | Rotate/purge logs, resize volume, add disk alert |
| 7 | `dns_failure` | DNS resolution failure | Restart CoreDNS, correct resolver config |
| 8 | `oom_killed` | JVM memory leak causing OOMKilled | Restart, apply heap limit, patch leaking cache |

### Resolution Time Distribution

Each family's 5 incidents show decreasing resolution time to simulate team learning:

- **Incident 1** (first encounter): 40–70 minutes
- **Incidents 2–5** (repeat encounters): 12–35 minutes

### Date Distribution

Incidents are spread across the 180 days prior to the generation date using random offsets.

### Excluded

The three demo incidents from `app.js` / `docs/DEMO_SCRIPT.md` are **not** included in the seed data to preserve a clean demonstration of memory learning.
